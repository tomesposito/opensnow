# opensnow — Technical Architecture Research for a Snowflake-like Cloud Data Warehouse

*Upfront research only — NOT a design decision. Codename: opensnow (“better, faster, freer”). Reader: technical founder / architect evaluating what it would actually take. Date of research: 2026-11-05. Method: web index search of primary docs, GitHub, vendor engineering blogs and papers (SIGMOD/VLDB). All URLs below are copied verbatim from sources consulted that day. Confidence flags: most engine/format facts are corroborated by ≥2 independent sources + primary docs; startup / effort claims are single-source or vendor-claimed and are flagged as such.*

---

## Summary — the blunt version in one page

1. **The query engine is no longer the hard, differentiating part.** Vectorized, columnar, push-based execution is a solved, open-source commodity: DuckDB (C++, MIT), DataFusion (Rust, Apache-2.0), ClickHouse (C++, Apache-2.0), Velox (C++, Apache-2.0, execution library only), Trino (Java, Apache-2.0), Doris/StarRocks (Java FE + C++ BE, Apache-2.0) all implement it, all beat row-at-a-time engines by an order of magnitude, and several have ClickBench / TPC-H proof at scale. Snowflake's own 2016 paper describes essentially this engine — in C++, push-based vectorized, over immutable columnar files on S3 — written from scratch at a time when none of these were usable. Today you would not write it from scratch unless execution *is* your research product.

2. **The storage / table-format layer is also largely commoditised — if you accept Iceberg (or Delta) + Parquet on object storage.** That stack gives you, off the shelf: ACID snapshot commits, time travel, schema/partition evolution, hidden partitioning, and metadata-only (zero-copy) cloning *in principle*. It does **not** give you Snowflake's integrated experience of those features: compaction, snapshot expiry, orphan cleanup, clustering, credential vending, RBAC and scan planning have to be operated as a permanent service, forever, or tables degrade in weeks (small-files death spiral, manifest bloat, planning time from 200 ms to 45 s in documented cases).

3. **The services / catalog / metadata layer is Snowflake's actual moat, and it is the least commoditised layer.** Snowflake has used FoundationDB — a distributed, ACID, ordered key-value store — as its metadata backbone since 2014 for *everything*: catalog, users/roles, locks and lock queues (via FDB watches), transaction state, per-file statistics, billing, query history. Features like zero-copy clone, time travel, data sharing, fail-safe and “metadata-only” queries are, in Snowflake's own words, “purely metadata operations” built on that layer. No open-source catalog (Polaris, Nessie, Lakekeeper, Unity Catalog OSS, Gravitino) replicates that scope: they do Iceberg REST commits + credential vending + (partial) RBAC, not sessions, transactions across objects, workload management, billing, lineage/access history, or a global optimizer's statistics store. DuckLake / Postgres-as-catalog is the closest conceptual shortcut — put metadata in a real transactional SQL database — and it is instructive that both DuckLake and many modern control planes (Neon, Supabase, MotherDuck-style designs in public write-ups) re-discover the same idea Snowflake took with FDB.

4. **Distributed execution is where projects stall.** Single-node engines are astonishingly good — a modern 32–128 vCPU box with NVMe and spilling handles tens to hundreds of GB and many TB-scale scans — and MotherDuck's whole thesis is that hypertenancy (one isolated single-node DuckDB per user/customer, “Ducklings”) avoids distributed execution entirely for most workloads. The moment you need a *single query* split across nodes, or many concurrent heavy queries with isolation, fairness, shuffle, fault tolerance and skew handling, you inherit the hardest distributed-systems problem in databases. Ballista proves DataFusion *can* be distributed, but its own ecosystem notes say most users build their own scheduler on top of it; Bauplan forked DuckDB, hit its I/O-control and Iceberg limits, and migrated to DataFusion; attempts to “just distribute DuckDB” repeatedly become forks that cost more to maintain than the engine saved. Trino, Spark, ClickHouse and Doris/StarRocks already solved this — at the price of operating a full MPP cluster product, not embedding a library.

5. **Therefore the realistic archetypes are assemblies, not inventions** (Section 8): (A) DuckDB-centric / hypertenant, (B) DataFusion-native Rust, (C) ClickHouse-fork / adopt, (D) Iceberg + Trino/Spark lakehouse. They differ mainly in *which* hard problem you choose to own: concurrency/distribution (A), scheduler + services (B), dialect + cloud separation retro-fit (C), or integration/operations tax (D). None gives you Snowflake parity — multi-cluster shared-data, virtual-warehouse isolation, result/metadata/local caches, global optimizer, sharing, governance — in < a year with a small team. Practitioner/vendor estimates found for a *production-grade DIY lakehouse assembly alone* (no new engine) are 3–6 FTE and 6+ months before functional, ~30–40 %/yr ongoing maintenance, ~$520k/yr organisational maintenance cost in one Wakefield/Onehouse-cited study — treat as directional, vendor-sourced.

## 1. Query Engines

**Common ground first.** All serious candidates share: columnar storage/layout, vectorized execution (process a batch — DuckDB: 2,048 values — that fits L1/L2 cache, use SIMD, avoid per-row virtual calls), predicate/projection pushdown to the scan, and late materialisation. Snowflake: “push-based vectorized query processing”, PAX/hybrid-columnar micro-partitions. Velox / Photon / DataFusion papers make the same argument: unify execution, don't re-implement it per engine. The differences that matter for opensnow are: *language & embeddability, pull vs push / streaming model, spilling & memory arbitration, concurrency model, distributed story, SQL dialect completeness, optimizer maturity.*

### 1.1 DuckDB
- **What / architecture (C++):** In-process, embedded OLAP DBMS — “SQLite for analytics”. No server, no daemon; linked into Python/R/Java/Node/Go/Rust/Wasm host. Columnar-vectorized engine, vectors of ~2,048, morsel-driven parallelism (workers claim ~122,880-row morsels), MVCC, single-file native format plus direct Parquet/CSV/JSON/Arrow querying. Push-based pipelining in its modern engine; operators stream vectors through pipelines, blocking operators (hash join/aggregate/sort) materialise + spill.
- **Out-of-core / spilling:** Real, not marketing. Buffer manager pages base data; hash tables, sorts, aggregations spill to `temp_directory` up to `max_temp_directory_size` (90 % disk default in docs cited); unified memory management in recent versions. Caveats sourced: some aggregates (e.g. `string_agg`) don't spill, multiple blocking operators can still OOM. Sources: DuckDB tuning / internals discussions summarised at https://pub.titasbiswas.com/series/every-record-counts/every-record-counts-s1-part-11-you-might-not-need-a-cluster/ and https://duckdb.org/docs/2.0/sql/data_types/overview
- **Extensions / lake:** `httpfs` (S3/GCS/Azure/HTTP, range reads), `iceberg`, `delta`, `ducklake`, `postgres`/`mysql`/`sqlite` scanners, `spatial`, `fts`, `json`, `avro`. Reads/writes Iceberg (merge-on-read only for UPDATE/DELETE/MERGE in the 2.0-era docs cited — positional deletes, fails if table is copy-on-write mode; plan compaction). Zero-copy Arrow interchange with Polars/pandas.
- **Concurrency / limits — blunt:** **One writer per database file (file lock), one node, no built-in auth, connection pooling, admission control, or HA failover.** MVCC gives snapshot readers inside one process, not a multi-user serving tier. Production write-ups are explicit: “Do not use it for concurrent writers, multi-user serving, or data that outgrows one node” — https://roosterpodlog.substack.com/p/duckdb-in-production-where-it-fits ; also https://medium.com/@indomitability/why-starrocks-is-better-than-duckdb-for-marketing-analytics-and-campaign-attribution-883f52b13112 . Scale-up works astonishingly far (tens–low hundreds GB comfortably, TB with spill/NVMe), scale-out does not exist natively.
- **Newer escape hatches:** *Quack* remote protocol (introduced 1.5.3, polished in 2.0, **beta, protocol not yet stable** per DuckDB FAQ https://duckdb.org/quack/faq) gives client-server DuckDB; *DuckLake* (see §2.6) moves catalog to Postgres. Neither is a distributed executor.
- **Maturity / production:** Very mature single-node. GitHub: https://github.com/duckdb/duckdb/ — MIT, IP held by non-profit DuckDB Foundation, “no enterprise version” https://duckdb.org/faq . Used embedded everywhere; as a *warehouse* only via MotherDuck (see §6.1) or DIY hypertenancy.
- **License:** MIT.
- **Verdict: CORE CANDIDATE — as the single-node engine / per-tenant engine, NOT as the distributed warehouse engine.** If opensnow's bet is “most workloads don't need a cluster”, DuckDB is the fastest path to a credible product. If the bet is Snowflake-parity MPP, DuckDB is a component at the leaf, not the system.

### 1.2 Apache DataFusion (+ Ballista, Comet)
- **What / architecture (Rust):** *Not a database — a query-engine toolkit / library for building databases.* Apache top-level project (graduated 2024). Arrow-native end-to-end: SQL parser (`sqlparser-rs`) → logical plan → rule + cost-based optimizer → physical `ExecutionPlan` → partitioned async streams (`Tokio`), producing Arrow `RecordBatch`es with no internal row format or serialisation between operators. SIGMOD Companion 2024 paper documents **>16 extension APIs** (`TableProvider`, `OptimizerRule`, `ExecutionPlan`, UDF/UDAF, catalog, etc.). Sources: https://datafusion.apache.org/user-guide/introduction.html ; optimizer: https://datafusion.apache.org/library-user-guide/query-optimizer.html
- **Execution model:** Streaming, multi-threaded, vectorized; pull/streaming via async `Stream`s (contrasts DuckDB's push pipelines — in practice both pipeline; difference matters for back-pressure and for embedding). Memory pool + spill infrastructure exists; hash-join spilling has been an active, incomplete area (see GitHub proposal discussion https://github.com/apache/datafusion/issues/17267) — do not assume DuckDB/ClickHouse-grade spill maturity for every operator.
- **Distributed: Ballista.** Scheduler + executors, gRPC/protobuf plans, Arrow IPC shuffle files, Arrow Flight SQL. Scheduler breaks plan into stages, dispatches *slices* of partitions to executors advertising vcores. Docs themselves / ecosystem analyses note: “Many Ballista users have their own distributed query engines that use Ballista as a foundation, rather than using Ballista directly” and “DataFusion itself runs on a single node. It doesn't include a scheduler, shuffle, or cluster manager” — https://datafusion.apache.org/ballista/contributors-guide/architecture.html ; analysis: https://medium.com/@thenextcompute/datafusion-is-becoming-the-linux-kernel-of-query-engines-bf9ff76bb09d
- **Comet:** Apple-donated Spark accelerator: Spark keeps scheduling/fault tolerance, Comet translates Spark physical plans to DataFusion native execution (JNI, Arrow zero-copy), claimed >2.2× TPC-H vs vanilla Spark in project materials. Lesson: even DataFusion's flagship distributed success *borrows Spark's distribution* rather than Ballista's.
- **Who uses it in production as / in a warehouse-like system:** InfluxDB 3.0 (query engine, time-series predicate pushdown), GreptimeDB, HoraeDB/CeresDB, CnosDB, ParadeDB (Postgres analytics — note ParadeDB itself is AGPLv3), Spice.ai, Seafowl, Cube Store, VegaFusion, delta-rs & iceberg-rust TableProviders, Arroyo/Cloudflare Pipelines (streaming), dbt Fusion (SDF acquisition, SQL compilation), Bauplan (see §6). List corroborated at https://datafusion.apache.org/user-guide/introduction.html
- **Strengths / limits:** Most extensible, most composable, Rust memory safety/no GC, fastest-growing builder ecosystem, reported fastest single-node Parquet on ClickBench in late 2024 (project claim). Limits: you own catalog, auth, concurrency/admission, scheduler, shuffle service, fault tolerance, SQL dialect surface beyond core, and operational tooling; deep customisation requires Rust (steeper hiring pool than SQL/Java); distributed is DIY.
- **License:** Apache-2.0.
- **Verdict: CORE CANDIDATE — the strongest “build a new warehouse” foundation if the team is Rust-first and wants to own the planner/optimizer.** It gives you ~80 % of a single-node engine for free (as its advocates put it) and 0 % of a cloud service.

### 1.3 ClickHouse (+ chDB)
- **What / architecture (C++):** Server OLAP DBMS from Yandex (Metrica), open-sourced 2016 Apache-2.0 https://clickhouse.com/blog/yandex-opensources-click-house . Columnar, vectorized (blocks/vectors, SIMD), MergeTree family: inserts write immutable sorted *parts* (sparse primary index: one mark per granule, 8,192 rows default), background merges consolidate; variants Replacing/Summing/Aggregating/Collapsing + ReplicatedMergeTree coordinated by ClickHouse Keeper (ZooKeeper replacement, Raft — coordination/replication log, leader election, DDL queue via ON CLUSTER).
- **Shared-nothing origins → Cloud separation:** OSS is shared-nothing/sharded (Distributed table fans out, manual resharding pain is real). ClickHouse Cloud is a *different, proprietary* engine: SharedMergeTree on object storage (S3/GCS/Azure), stateless compute, local SSD only as cache, Keeper for metadata/coordination, and in 2025–26 a Shared Catalog removing last local-disk dependency for DDL — vendor account: https://clickhouse.com/blog/clickhouse-cloud-stateless-compute . **Critical build-vs-borrow fact: SharedMergeTree / Shared Catalog are NOT in OSS ClickHouse.** Forking OSS does not give you Cloud.
- **SQL dialect:** Powerful but idiosyncratic — ClickHouse SQL, not ANSI/Postgres/Snowflake; many functions/types differ, JOIN and mutation (`ALTER … UPDATE/DELETE` as async mutations, lightweight updates only recent/beta in 26.x write-ups) semantics surprise warehouse migrants. High concurrency & high ingest are its superpowers (event/analytics serving, observability — e.g. Cloudflare-scale stories cited by vendor).
- **chDB:** Embedded ClickHouse engine as a library (`libchdb`, Python/Node/Go/Rust), “ClickHouse without a server”. Evaluations found: ~326 MB dynamic / 490 MB static artifact, Rust binding self-labelled experimental, no Delta table function in embedded build in one conformance eval https://github.com/chandlerok/feather/blob/HEAD/docs/engine-and-format-decisions.md . Useful as embedded scan engine for ClickHouse-dialect users; not a warehouse foundation by itself.
- **Concurrency / spill / cache:** Server-grade concurrency, admission via quotas/profiles, mark/primary-index + OS page cache + local caches; memory is the operational cliff (vendor guidance 32 GB+ recommended in comparisons). Queries can be killed on memory limits rather than gracefully spilling everything — plan for it.
- **License:** Apache-2.0 (core).
- **Verdict: CORE CANDIDATE / ADOPT-DON'T-FORK — if opensnow's workload is real-time event analytics, high-concurrency dashboards, append-heavy, ClickHouse *as-is* is the closest OSS thing to a production warehouse today.** As a Snowflake clone (general SQL warehouse, semi-structured, time travel/clone/share, ANSI dialect) it is a reference + component, and forking it to add Snowflake semantics repeats Firebolt/Cloud's multi-year proprietary effort.

### 1.4 Apache Polars
- **What:** Rust DataFrame library (not a SQL warehouse), Arrow-native (own Arrow-compatible memory), lazy query planner (projection/predicate pushdown, fusion), multi-threaded vectorized kernels, streaming/out-of-core engine (default in Polars 2.0-era write-ups, ~80 % RAM budget, spills). Python-first UX is the product.
- **Vs DataFusion:** DataFusion FAQ itself: Polars is among fastest DataFrames, Rust + Arrow like DataFusion, but “not designed with as many extension points”, no SQL-first/catalog system-builder surface https://arrow.apache.org/datafusion/user-guide/faq.html . One comparison (single-source, treat cautiously) claims DataFusion ~3× Polars at TPC-H SF500 larger-than-memory.
- **License:** MIT (core Rust/Python).
- **Verdict: COMPONENT / REFERENCE ONLY for a warehouse.** Excellent embedded/ETL and notebook engine, plausible leaf executor or Polars-API surface; no catalog, transactions, server, distributed SQL, or governance to build a warehouse *on* without re-creating DataFusion/DuckDB around it.

### 1.5 Meta Velox (+ Prestissimo, Gluten)
- **What / architecture (C++):** *Execution library only* — no SQL parser, no planner/optimizer, no scheduler, no catalog. Reusable vectorized operators, expression evaluation, DWIO readers/writers, memory pools/arbitration + spilling, connectors. Created to stop Meta re-implementing the same (inconsistent!) string/date functions in Presto, Spark, stream processing. Paper: Pedreira et al., “Velox: Meta's Unified Execution Engine”, PVLDB 15(12) 2022, cited at https://github.com/sujithjay/sujithjay.github.io/commit/d04d519c875d0d39451b5f92f8b7812e9f7ca2bb ; repo https://github.com/facebookincubator/velox (via PyVelox page https://pypi.org/project/pyvelox/0.0.1a7/ — Apache-2.0).
- **Integration proof:** Prestissimo = Presto Java coordinator + Velox C++ workers (drop-in replacement, fully rolled out at Meta per VLDB 2026 paper https://upenn.ferric.systems/dbscholar/vldb_papers/2026/p4399-dutta.pdf); Gluten = Spark + Velox; Comet is the DataFusion analogue of Gluten. GPU extension work shows Velox operators can be re-targeted (cuDF) https://arxiv.org/html/2606.24647 .
- **Verdict: COMPONENT — superb if you already have a planner/coordinator (Trino/Presto/Spark) and need a native worker; a trap if you don't.** Choosing Velox as “the engine” means you still must choose/build everything above it (SQL, optimizer, coordinator, scheduler) — that's a Presto-sized project.

### 1.6 Trino / Presto
- **What / architecture (Java):** Federated MPP SQL engine. One coordinator (parse, analyse, plan, schedule stages/tasks) + many stateless workers; workers pull data via *connectors* (Iceberg/Delta/Hudi/Hive, Postgres/MySQL, Kafka, Cassandra, …), process in memory, exchange intermediate data over HTTP. No storage of its own. Fork history matters: PrestoDB (Meta, Presto Foundation) vs Trino (original creators, ex-PrestoSQL, renamed 2020). Sources: https://motherduck.com/glossary/trino/ ; https://www.cloudera.com/resources/faqs/what-is-trino.html
- **Strengths:** Best-in-class federation (join across catalogs in one query), mature distributed joins/aggregations, fault-tolerant execution mode in recent Trino, huge connector ecosystem, ANSI SQL. Proven at petabyte/exabyte interactive scale.
- **Limits for opensnow:** It's a query engine, not a warehouse: no native storage/transactions — transactions, cloning, sharing, governance live in the table format + catalog underneath; JVM memory/GC tuning, coordinator is a scaling/HA design point; resource groups give workload isolation but not Snowflake-style per-warehouse billing/suspend. Caching is add-on (Alluxio / connector caches), not integrated result+metadata+local cache.
- **License:** Apache-2.0.
- **Verdict: CORE CANDIDATE as the distributed execution layer in a lakehouse archetype (Iceberg + Trino), REFERENCE for federation design.** Fastest route to “distributed SQL that actually works on day 1” — if you accept Java/JVM and that everything else (storage services, ingestion, governance product) is still yours.

### 1.7 Apache Doris & StarRocks
- **What / architecture:** Real-time MPP warehouses, MySQL protocol/dialect. Two process types only: FE (Java — parsing, planning, metadata, coordination; Master/Follower/Observer) + BE/CN (C++ — columnar storage, fully vectorized, pipeline execution, runtime filters incl. bloom/min-max). Cost-based optimizer, distributed shuffle joins, materialised views / rollups, primary-key models for upserts. Doris intro: https://doris.apache.org/docs/2.1/gettingStarted/what-is-apache-doris/ ; StarRocks (Doris fork origin, claims ~90 % rewritten, new CBO, intelligent MVs): https://www.ssp.sh/blog/starrocks-lakehouse-native-joins/
- **Storage modes:** Both now offer shared-nothing (BE local storage) *and* shared-data (object storage, CNs with local cache only) — mirroring ClickHouse's evolution. Lake federation (Iceberg/Hudi/Hive, JDBC) is first-class.
- **Strengths / limits:** Sub-second, high-concurrency serving + streaming ingest + upserts in one system — arguably closer to “real-time Snowflake + ClickHouse” than either alone; strong in APAC production (and StarRocks at Coinbase/Pinterest per case write-ups). Limits: MySQL dialect ≠ Snowflake/ANSI migration story, FE metadata store is its own operational system, ecosystem/tooling/docs depth in English and cloud-service maturity lag ClickHouse/Trino, governance/sharing/time-travel-clone semantics are engine-native, not open-format portable.
- **License:** Apache-2.0 (both; check Doris third-party exceptions).
- **Verdict: CORE CANDIDATE / REFERENCE — evaluate seriously if real-time + concurrency is the wedge; otherwise component/reference.** Adopting Doris/StarRocks as-is is more plausible than forking them into a Snowflake dialect.

### 1.8 Others in one line each
- **Databend:** Rust, Arrow, complete warehouse system targeting end users (own engine, S3-native) — reference/competitor, Apache-2.0.
- **DuckDB alternatives summary:** chDB (above), DataFusion (library), Polars (DataFrame), GlareDB/Seafowl (DataFusion-based, largely stalled/absorbed — cautionary), LakeSail/Sail (Spark Connect on DataFusion).

## 2. Storage & Table Format Layer

### 2.0 Mapping Snowflake → open stack
Snowflake: tables → immutable, compressed, columnar **micro-partitions** (~50–500 MB uncompressed in secondary sources; ~16 MB files in the 2016 paper's era) in a proprietary PAX-like layout on S3/Azure/GCS, with per-micro-partition, per-column metadata (min/max, null count, distinct count) held **in the services layer (FDB)**, not in the files alone. Pruning = metadata check, no indexes. Open equivalent: **Parquet files (≈ micro-partitions) + Iceberg manifests/snapshots (≈ FDB file/statistics registry, but stored as files in object storage and cached by engines) + a catalog (pointer swap)**. That substitution — database-resident metadata → file-resident metadata + REST catalog — is the single most consequential architectural difference; it drives planning latency, commit contention, and why DuckLake (§2.6) exists.

### 2.1 Apache Parquet
- File = 1+ **row groups** (horizontal slices, ~128 MB typical) × **column chunks** (one column's values in that row group, contiguous) × **pages** (smallest encoded/compressed unit). Footer holds schema, row-group locations, per-column-chunk statistics (min/max, null count). Encodings: dictionary/RLE, delta-binary-packed, delta-length, byte-stream-split; then per-page compression: Snappy (default compat), ZSTD (best modern ratio/speed), GZIP/LZ4. Bloom filters per column chunk for high-cardinality equality pruning (off by default in many writers — enable deliberately). Readers do projection (read only needed columns) + predicate pushdown (skip row groups/pages whose stats can't match) — *but only if data is sorted/clustered on filter columns; random order = wide min/max = no pruning.* Sources: https://www.parseable.com/blog/observability-apache-parquet ; https://www.kargin-utkin.com/engineering-toolkit/file-formats/parquet
- **Verdict: CORE — non-negotiable substrate.** Also its limits define the roadmap: no transactions, no row identity, poor random access (see Lance), no update story — all of that is the table format's job.

### 2.2 Apache Iceberg — the default choice, in depth
- **Spec structure:** Catalog → `metadata.json` (schema, partition specs, sort orders, snapshot list; catalog stores only a pointer to current file, swapped atomically on commit = compare-and-swap) → per-snapshot **manifest list** (Avro; partition-range summaries to prune whole manifests) → **manifests** (Avro; per-data-file: path, partition tuple, record count, per-column lower/upper bounds, null counts) → data files (Parquet/ORC/Avro). Readers prune at manifest-list → manifest → file → row-group → page level. Sources: https://www.aicassindra.com/blogs/hive_impala/impala_iceberg.html ; https://dev.to/gabrielhca/apache-iceberg-in-production-compaction-catalogs-and-the-pitfalls-nobody-warns-you-about-3ml3
- **Snapshots / time travel / rollback:** Every commit = new immutable snapshot; readers get snapshot isolation without locks; query `AS OF` snapshot/timestamp, rollback by re-pointing. Retention is policy: expire snapshots or you pay for history forever.
- **Hidden partitioning + partition evolution:** Partition transforms (`identity, year/month/day/hour, bucket[N], truncate[W], void`) are applied by the engine from source columns — users filter on `ts`, not a derived `ts_date`. Spec can *evolve*: old files keep old spec, new writes use new spec, planning handles both — no rewrite. Schema evolution likewise by column ID (add/drop/rename/reorder/widen without rewriting).
- **Row-level deletes, v2 vs v3:** v2: position deletes + equality deletes (merge-on-read) or rewrite (copy-on-write). **v3 (adopted May 2025 in sources; engine support still uneven in late 2026):** (1) **Deletion vectors** — one binary bitmap per data file, stored in Puffin files, replaces position-delete files, far cheaper to apply; (2) **Row lineage** — stable `_row_id` + `_last_updated_sequence_number`, enabling incremental/CDC reads without diffing snapshots; (3) **VARIANT** type (+ geometry/geography, `timestamp_ns`), column defaults, multi-arg transforms. Support snapshot (Oct 2026 lab, single source https://pub.titasbiswas.com/series/every-record-counts/every-record-counts-s1-part-7-the-table-that-remembers/): Spark reads/writes v3, DuckDB 2.0 reads/writes most v3 (MoR only), Trino 484 v3 *experimental*, PyIceberg 0.12 partial / cannot upgrade past v2. **Design implication: default to v2 for interoperability, use v3 only where every reader/writer on that table supports it.**
- **Compaction & maintenance (the permanent tax):** `rewrite_data_files` (binpack/sort/z-order, target 128–512 MB), `rewrite_manifests`, `expire_snapshots`, `remove_orphan_files`. Without them: see §2.7. This is a *service you must build/operate* (Spark jobs today are the reference implementation; Trino/Flink/DuckDB shops often still run Spark just for maintenance).
- **Catalog types:** REST (the standard — see §3), Hive, JDBC, Hadoop, Glue, Nessie. REST decouples engine from catalog implementation via OpenAPI + credential vending / remote signing + (newer) server-side scan planning.
- **License:** Apache-2.0. Origin Netflix, Apache top-level.
- **Verdict: CORE — default table format for opensnow archetypes B/D, and the interop surface for A/C.** Its weakness is not features, it's operational physics (file-resident metadata, compaction, multi-engine version skew — mismatched Iceberg versions between Spark/Trino have produced silently incorrect results in cited DIY post-mortems).

### 2.3 Delta Lake
- Parquet files + **`_delta_log/`**: sequentially numbered JSON commits (actions: add/remove file + stats, protocol, txn IDs) + Parquet checkpoints every ~10 commits folding log state. Optimistic concurrency: writer writes files first, then tries to create next log file; conflict = retry/rebase. Features: ACID, time travel (`VERSION/TIMESTAMP AS OF`, `RESTORE`), schema enforcement/evolution + type widening, deletion vectors, Liquid Clustering (§4.5), **cloning**: shallow = metadata only, points at source files, independent log/history from clone point; deep = copies files https://delta.io/blog/delta-lake-clone/ . **UniForm:** asynchronously generates Iceberg (and Hudi) metadata for the same files so Iceberg readers can read Delta tables — requires Unity Catalog for full v3/UniForm path in Databricks materials https://link.springer.com/chapter/10.1007/979-8-8688-2524-8_15
- **Trade-offs:** Simpler mental model + best Spark/Databricks integration + delta-rs (Rust, DataFusion-based) for non-JVM; weaker multi-engine write interoperability than Iceberg, catalog/governance gravity toward Unity Catalog/Databricks, log replay/checkpoint behaviour at extreme table counts is its scaling story.
- **License:** Apache-2.0 (Linux Foundation).
- **Verdict: COMPONENT / ALTERNATIVE CORE — choose Delta if Spark/Databricks is the centre of gravity; otherwise Iceberg is the freer, more vendor-neutral bet the mission asks for.**

### 2.4 Apache Hudi & Apache Paimon (brief)
- **Hudi (Uber, Apache-2.0):** Built around record keys + timeline. Copy-on-write (rewrite files on update, fast reads) or merge-on-read (delta log files + base Parquet, compact later). Record index maps key → file group so upserts touch only relevant files; incremental queries (“what changed since instant X”) are native. Strength: streaming CDC/upsert-heavy lakes. Cost: Spark-centric, operational concepts (timeline, cleaning, compaction) are a second system to learn. https://hudi.apache.org/docs/storage_layouts/
- **Paimon (Alibaba/Flink, Apache-2.0, ex-Flink Table Store):** LSM-tree-organised primary-key tables, stream-native: Flink writes continuously, merge engines (deduplicate, partial-update, aggregation, first-row), changelog production for streaming reads. Strength: real-time warehouse on Flink. Cost: Flink-first ecosystem, smaller SQL-engine breadth than Iceberg.
- **Verdict (both): REFERENCE / COMPONENT for streaming-upsert niches; not the general opensnow table-format bet.**

### 2.5 Lance / LanceDB
- Rust columnar *file + table + (namespace) catalog* stack for multimodal/AI: fragments + manifest versioning (zero-copy snapshots like Iceberg, in-format), layout optimised for **random access (~100× Parquet claims, vendor)** and large blobs/vectors, native vector (IVF-PQ/HNSW), full-text and bitmap indexes stored with data. Apache-2.0; production at AI companies for embeddings/media (vendor-cited). Creators' own framing quoted in sources: “Lance for AI and Iceberg for BI.” https://zilliz.com/ai-faq/lance-vs-vortex ; also Vortex (Linux Foundation) is the neighbouring Parquet-successor experiment for fast scans/compression.
- **Verdict: COMPONENT for an AI/vector product line (embeddings, multimodal, random-access serving); REFERENCE ONLY for the SQL warehouse core.** DuckDB 1.5+ adding Lance support makes it a plausible sidecar format, not a replacement.

### 2.6 DuckLake — the instructive heresy
- DuckDB Labs, MIT, spec 1.0 Apr 2026: **all metadata (snapshots, schemas, file lists, statistics — 28 catalog tables in spec 1) lives in a SQL database (Postgres/SQLite/DuckDB file); only Parquet lives in object storage.** Commit = one SQL transaction (multi-table ACID for free, no manifest files, planning = one indexed query, milliseconds). Data inlining (small writes staged in catalog DB, default ≤10 rows in v1 materials) directly attacks small-files. Clients: DuckDB reference, plus DataFusion/Spark/Trino readers at varying maturity. Sources: https://motherduck.com/blog/ducklake-architecture-deep-dive/ ; https://www.factualminds.com/blog/ducklake-vs-apache-iceberg-on-aws-2026/
- **Verdict: CORE CANDIDATE for Archetype A, and the best live experiment in “Snowflake was right about metadata-in-a-database”.** Risks: single-vendor spec gravity (DuckDB Labs → AWS in 2026 announcements, IP stays in Foundation per FAQ), multi-engine write maturity, Postgres catalog becomes your scaling/HA bottleneck to engineer — exactly the FDB problem, in miniature.

### 2.7 Object storage layer — physics and money
- S3/GCS/Azure Blob: effectively infinite, cheap capacity ($0.023/GB-month S3 Standard us-east-1 list in source), strong read-after-write consistency (modern S3/GCS), **but**: high per-request latency (~10s–100 ms), no rename, LIST is expensive and slow, range GETs are the fast path. Request pricing asymmetry matters: PUT/COPY/POST/LIST $0.005/1,000 vs GET $0.0004/1,000 (>12×) — https://alexmerced.blog/blog/2026-09-10-iceberg-maintenance-budget.html
- **Small-files problem, quantified from sources:** each file ≈ 200 ms metadata/footer overhead on S3 in one analysis; 100k files = 100k tasks (1–10 ms scheduling each), 200k GETs ≈ $0.08/query → $800/day at 10k queries/day vs ~$16/day compacted to 2k files in that worked example; streaming checkpoints (100 partitions × 10 min) = 14,400 files/day. Compaction fixes reads but is write amplification: read all + write new + temporarily ~2× storage until expiry. Sources: https://medium.com/towards-data-engineering/the-spark-small-file-problem-why-compaction-is-a-recurring-tax-e652023c6dd4?source=topic_portal---latest_stories---apache_spark---0------------------------------------- ; https://github.com/iomete/iom-docs/blob/HEAD/blog/2026-01-17-apache-iceberg-production-antipatterns-2026.md
- **Implication:** File sizing (128–512 MB), partition discipline, compaction triggers, and metadata caching are *cost architecture*, not tuning. GCS/Azure differ in request pricing/consistency details and egress — multi-cloud opensnow must abstract `object_store` (Arrow Rust crate / DuckDB httpfs do) and never assume S3 semantics in the catalog layer.

### 2.8 Zero-copy cloning, time travel, sharing on Iceberg — how you'd actually build Snowflake's features
- **Time travel:** free from snapshots: resolve timestamp → snapshot ID at planning, scan that snapshot's manifests. Retention/expiry *is* the product knob (Snowflake: 1 day Standard, up to 90 Enterprise + 7-day Fail-safe — Fail-safe, a Snowflake-only recovery copy, has **no** Iceberg equivalent; you'd emulate with longer snapshot retention + backup).
- **Zero-copy clone:** create new table/catalog entry whose initial snapshot references the *same* manifest list / data files as source snapshot; subsequent writes to either table create new files/snapshots, divergence is copy-on-write at file granularity. Snowflake does exactly this at micro-partition level and documents clone for Iceberg tables too — but only for *Snowflake-managed* Iceberg tables, with Horizon REST access needing extra grants: https://docs.Snowflake.com/en/sql-reference/sql/create-iceberg-table-snowflake ; general clone semantics: https://docs.snowflake.com/en/user-guide/dynamic-tables/cloning . **Gotchas you inherit:** file lifecycle/ref-counting (expiring source snapshots must not delete files a clone still references — Iceberg catalogs don't natively ref-count across tables; you need a protection/GC layer above snapshots), branch/tag semantics help (clone from a tag for reproducibility), and cross-account sharing needs credential vending per consumer.
- **Branches/tags (Iceberg refs):** branch = mutable named ref to a snapshot lineage (write-audit-publish: write to branch, validate, fast-forward main); tag = immutable named ref (audit/release baseline). This is the substrate for dbt-style dev/prod environments without copying data.
- **Data sharing:** Snowflake Secure Sharing = grant a *consumer account* read access to provider's metadata-defined objects, no data copy, provider pays storage, consumer pays compute, revoked instantly. On Iceberg: share the catalog namespace with scoped, vended credentials (Polaris principal/roles, §3) or share snapshot/branch refs via a second catalog; the consumer's engine reads provider's bucket with short-lived STS tokens. What you must build: identity federation across organisations, row/column policy propagation (not in Iceberg spec — catalog/engine layer), usage metering per consumer, and revocation that actually invalidates vended creds/caches. Snowflake's own move — Horizon Catalog built on Polaris, Open Catalog — is evidence even Snowflake implements Iceberg sharing *through Polaris*, not by opening its native format.

## 3. Catalog & Metadata / Cloud Services Layer — “the secret sauce”

### 3.1 What a catalog must do (beyond “list tables”)
For a Snowflake-like product the services layer must provide, transactionally and multi-tenantly: (1) atomic table commits (CAS on metadata pointer, conflict detection/retries, multi-table transactions for clone/branch merge); (2) catalog objects: databases/schemas/tables/views/functions/roles/users/shares/stages/tasks — with DDL concurrency and schema evolution/versioning of the metadata itself; (3) optimizer statistics (per-file/per-column min/max/nulls/distinct, histograms) fresh enough to prune and join-order well; (4) RBAC + governance: grants graph, row-access policies, masking, tags, classification; (5) lineage + access history (every statement, every file accessed — Snowflake stores a metadata entry for *every statement executed* per its FDB blog); (6) locks/queues, session/transaction state, idempotency/retry; (7) billing/metering, query history, result-cache registry. **An Iceberg catalog does (1) for tables and part of (3). Everything else is opensnow product to build.**

### 3.3 Metadata store choices — the control plane database
- **FoundationDB (what Snowflake actually uses):** See §9 for full treatment. Ordered, distributed, strictly serializable KV, triple-replicated across AZs, simulation-tested. Snowflake since 2014; object-mapping layer on top (Java library per engineer comments); watches implement lock queues. FDB is Apache-2.0 (Apple) and *available* to opensnow — but operating FDB well (recruitment, tuning, layer design) is a specialist commitment, and you still build every layer Snowflake built on it.
- **Postgres as control plane:** The pragmatic default in 2026. DuckLake puts *table* metadata in Postgres; Neon/Supabase/MotherDuck-style architectures in public write-ups use Postgres for tenant/catalog/billing metadata (operational familiarity, transactions, point-in-time recovery, hosted options everywhere — Aurora/RDS/Cloud SQL/AlloyDB, Neon serverless branching). Pattern in sources: Supabase Postgres as DuckLake catalog via `ATTACH 'ducklake:postgres:…'` https://motherduck.com/blog/spark-ducklake-getting-started/ . Limits: single-primary write scaling, HA/failover is your cloud's story, cross-region active-active is not Postgres's story — fine until global control plane is a requirement, then you're back to FDB/Spanner-class systems.
- **Others:** etcd (small, Raft KV — Ballista scheduler can use it for HA state; too small/opinionated for full catalog), CockroachDB (distributed SQL, Postgres-ish wire, serializable — plausible FDB-alternative with SQL ergonomics; licensing: core moved to source-available/enterprise terms in recent years — *verify current terms before betting*), TiKV / FoundationDB layers, DynamoDB/Cassandra (Snowflake did *not* choose eventual consistency for metadata — that tells you the requirement), Spanner (only on GCP, proprietary).
- **Verdict:** **Postgres (or Cockroach) for v1 control plane + Polaris for Iceberg commits is the borrow-maximising path; FDB is the Snowflake-faithful path and a multi-year expertise bet.** Either way the *schema and object-mapping layer* on top — versioned metadata objects, backwards-compatible evolution, blue-green metadata upgrades à la Snowflake paper — is yours.

### 3.4 Multi-tenancy isolation models
Three models seen in production: (a) **Shared services + shared compute pools with resource groups/quotas** (Snowflake services layer is fully multi-tenant; compute is isolated per virtual warehouse — tenant isolation at compute, sharing at services/storage); (b) **Hypertenancy** (MotherDuck: per-user/customer isolated single-node instance on shared storage — isolation by construction, no workload manager, cost = fleet management + per-instance overhead); (c) **Siloed** (per-tenant catalog namespace + per-tenant bucket/prefix + per-tenant compute namespace in K8s — strongest blast-radius/compliance story, highest ops cost). Cross-cutting requirements regardless of model: per-tenant encryption keys, noisy-neighbour admission control, per-tenant metering that survives retries, and data-residency pinning. No OSS catalog gives you tenant lifecycle (provision/suspend/delete/GDPR-erase across snapshots+clones+shares) — that workflow is product.

## 4. Distributed Execution & Scaling — the hardest part

### 4.1 What “distributed” actually adds
Shuffle (repartition by join/group key over the network — usually the dominant cost), distributed join strategies (broadcast vs shuffle-hash vs sort-merge, chosen by statistics), distributed aggregation (partial/final), stage scheduling with locality + skew handling, fault tolerance (stage retry vs query restart vs Snowflake/BigQuery-style shuffle persistence), adaptive execution (runtime statistics reshaping plans — Doris/DataFusion dynamic filters), and a *global* optimizer that knows data distribution. A single-node engine has none of these problems; that is precisely why it is fast to build and pleasant to run.

### 4.2 Optimizers: Calcite vs DataFusion vs bespoke
- **Apache Calcite (Java, Apache-2.0):** Reusable planner framework — relational algebra, rule-based (Hep) + cost-based (Volcano/Cascades-style) planners, pluggable cost/metadata, adapters. Powers Hive/Flink/Druid/Drill planning. No execution. Choose it if your coordinator is JVM (Trino-like) — https://calcite.incubator.apache.org/javadocAggregate/org/apache/calcite/plan/package-summary.html
- **DataFusion optimizer:** Rule + emerging cost model in Rust; extensible `OptimizerRule`/`PhysicalOptimizerRule`, statistics via `ColumnStatistics` (nulls, bounds, distinct), interval/boundary analysis for selectivity. Honest assessment from sources: predicate/projection pushdown and join reordering are solid; full Cascades-style cost-based join ordering for complex multi-join warehouse queries is *younger* than Calcite/Spark Catalyst/Snowflake's optimizer — and Snowflake's optimizer (top-k pruning, join ordering search, pruning over FDB statistics) is a decade-deep asset (§9). https://datafusion.apache.org/library-user-guide/query-optimizer.html
- **Spark Catalyst / Trino / Doris-StarRocks CBO / ClickHouse:** Each mature engine ships its own — another argument for adopting an engine over assembling one: the optimizer *is* the product in warehouse benchmarks.
- **Substrait:** Cross-engine plan IR — the escape hatch that lets Calcite-frontend → DataFusion/Velox execution compose; integration coverage is still partial in practice (CMU course project found 15/21 TPC-H Substrait plans ran on DataFusion via Isthmus https://github.com/apache/datafusion/issues/14373).

### 4.3 Execution substrates compared
- **Ballista:** §1.2. Pros: Rust/Arrow-native, K8s/Docker deploy, etcd-backed scheduler HA path. Cons: smaller production footprint, you become the distributed-systems team. **Verdict: component/proving ground, not a Snowflake-grade scheduler off the shelf.**
- **Apache Spark as substrate:** Pros: battle-tested shuffle, fault tolerance, streaming, Iceberg/Delta maintenance actions, and native accelerators (Comet=DataFusion, Gluten=Velox) give you vectorized execution *inside* Spark's distribution — the lowest-risk way to get distributed DataFusion/Velox today. Cons: JVM/job-startup latency, batch/job (not interactive query) heritage, Spark SQL dialect/optimizer owns your semantics unless you bypass it, operating Spark is its own platform. Sources: https://apxml.com/courses/advanced-ai-infrastructure-design-optimization/chapter-5-scalable-data-feature-engineering/data-processing-spark-ray
- **Ray:** General distributed Python (tasks/actors, shared-memory object store). Ray Data is a data-interchange/ML layer, not a SQL optimizer/warehouse executor. **Verdict: reference/component for Python/ML pipelines feeding the warehouse; not the SQL execution substrate.**
- **Native distributed DuckDB efforts:** No OSS native distributed DuckDB exists. Patterns are: (i) hypertenancy (MotherDuck), (ii) fork + split scans from execution (Bauplan's `EXPLAIN SCANS` fork — abandoned for DataFusion), (iii) DeepSeek **smallpond** — distributed data-processing *framework* on DuckDB + 3FS (each node runs DuckDB locally over shared storage) — a batch framework, not a concurrent SQL warehouse https://davidgasquez.github.io/awesome-duckdb/ , (iv) external orchestrators (Daft, Hamilton, etc.) partitioning work across DuckDB instances. **Lesson: every successful “distributed DuckDB” is actually a distributed *orchestrator over* single-node DuckDB, with the orchestrator owning partitioning/shuffle semantics.**
- **ClickHouse Distributed / Trino model:** §1.3/§1.6 — both prove MPP over (originally) local or (now) object storage; Trino's coordinator/worker + connector model is the cleanest reference design for opensnow's own coordinator if you build one.

### 4.4 Workload isolation like virtual warehouses — provisioning mechanics
Snowflake virtual warehouse = independently sized (XS–6XL), multi-cluster (for concurrency), auto-suspend (default minutes) / auto-resume, per-second billing (60 s minimum in Snowflake's model), isolated local SSD cache per warehouse. Reproducing it:
- **Kubernetes:** namespace/pool per warehouse, pod per engine instance (Trino worker sets, DataFusion executors, DuckDB “ducklings”), HPA/KEDA on queue depth, node pools by instance family (compute- vs memory-optimised). Cold start = image pull + engine start + catalog attach + cache warm — seconds to tens of seconds unless you cheat (below).
- **Warm pools:** pre-started, catalog-attached, idle instances claimed in <1 s (pattern now standard in sandbox infra: warm-pool claim via queue/`SKIP LOCKED`, TTL recycling — documented for Fly/Daytona/Modal-style systems at https://github.com/kuanpak/enterprise-harness-agents/blob/HEAD/research/sandbox-mgmt.md). MotherDuck claims ~100 ms Duckling spin-up (vendor) — single-node process start is fundamentally easier than cluster start; a multi-node warehouse cannot resume that fast, which is why Snowflake multi-cluster scaling lags and why per-query serverless (BigQuery slots) is a different product shape.
- **Firecracker / microVMs:** ~125 ms boot, snapshot/restore in tens of ms, KVM-grade tenant isolation, Apache-2.0 — the Lambda substrate; AWS Lambda MicroVMs now productise launch/suspend/resume + per-second compute billing on Firecracker https://aws.amazon.com/jp/lambda/lambda-microvms/ . Fit: per-tenant DuckDB/DataFusion instances (strong isolation, fast resume from snapshot with warm page cache). Cost: you operate the Firecracker fleet (or pay AWS/Fly/e2b), snapshots are tied to version/CPU template.
- **Containers (plain K8s pods):** weaker isolation (shared kernel), fastest density; acceptable for trusted/internal tenants, not for arbitrary-code / regulated multi-tenancy.
- **Per-second billing mechanics (build it yourself):** meter at the *services* layer — instance-seconds × size multiplier, plus storage GB-months, plus request/egress pass-through; requires idempotent metering events tied to query IDs in the metadata store (Snowflake: every statement has an FDB entry — metering falls out of that design), minimum-billing rules, credit holds/admission when balances exhaust, and suspend/resume accounting that doesn't double-count warm-pool idle (decide: warm pool is *your* cost centre, not the tenant's).

### 4.5 Caching layers — how Snowflake does it, how you'd copy it
Snowflake's three caches (corroborated across docs summaries https://www.flexera.com/blog/finops/snowflake-query-tuning-part1/ ; https://www.catobyte.co/en/guides/snowflake_study_guide.html):
1. **Result cache (services layer):** exact-query results for 24 h (renewed on reuse, max 31 days), shared across warehouses/roles, served with *no warehouse running*, invalidated on any underlying data change.
2. **Local disk / warehouse cache (compute SSD):** micro-partitions fetched from object storage cached on warehouse nodes; lost on suspend — hence auto-suspend is a cost-vs-warm-cache trade-off users feel.
3. **Metadata cache (services layer):** row counts, min/max, distinct counts — answers `COUNT(*)`/`MIN`/`MAX` and drives pruning with no compute (“metadata-only queries”).
Open-stack equivalents: result cache = services-layer store keyed by (normalised SQL, snapshot IDs of all inputs, role/policy version) in e.g. Redis/S3 + metadata DB — *invalidation correctness is the hard part*; local cache = engine-local NVMe file cache (ClickHouse/StarRocks/Doris shared-data CNs do exactly this; Trino via Alluxio/RaptorX-style caches; DataFusion/DuckDB: OS page cache + explicit file cache you build); metadata cache = catalog statistics service (§3) with engine-side manifest/statistics caching (Iceberg REST scan-planning helps centralise it). **No OSS engine ships all three integrated — this is a concrete, buildable differentiator that is still months of work.**

### 4.6 Search optimisation / indexing on columnar data
No B-trees in lake warehouses. The toolkit is *data skipping + layout*:
- **Min-max / zone maps** at every level (Parquet row group, Iceberg manifest/file, Snowflake micro-partition) — only works with clustering.
- **Bloom filters** (Parquet column chunk, Iceberg Puffin, Hudi metadata table) for high-cardinality equality: “definitely absent” skips the file. https://jack-vanlightly.com/blog/2025/10/8/beyond-indexes-how-open-table-formats-optimize-query-performance
- **Clustering / sort orders:** single-key sort (Iceberg sort orders, ClickHouse ORDER BY), **Z-order** (multi-dimensional space-filling curve, Delta `OPTIMIZE … ZORDER BY`), **Liquid Clustering** (Delta/Databricks: `CLUSTER BY` declared on table, incremental reclustering during OPTIMIZE, keys changeable without full rewrite, `CLUSTER BY AUTO` from query history — replaces partitioning + Z-order in Databricks guidance https://docs.databricks.com/aws/en/optimizations).
- **Snowflake analogues to study:** automatic clustering (background reclustering service — another permanent background service to build), search optimisation service (point-lookup indexes over micro-partitions, incl. semi-structured paths), query acceleration service (offload/scale-out for spiky queries).
- **Firebolt's lesson:** sparse primary + aggregating + join indexes over its F3 format prune to *ranges far smaller than micro-partitions* — evidence that “no indexes” is a choice, not a law, and that selective/customer-facing workloads reward real indexing https://www.firebolt.io/comparison/firebolt-vs-redshift
- **Verdict:** layout + skipping is CORE and mostly borrowed (compaction service enforces it); true secondary/search indexes are a BUILD differentiator for point-lookup / customer-facing archetypes.

## 5. Ingestion, Streaming & Semi-Structured

### 5.1 Snowpipe-like continuous ingestion on an open stack
Snowpipe = file-staged micro-batch auto-ingest (event notifications → queue → per-file load, per-second-ish billing) + Snowpipe Streaming = SDK/Kafka-connector row streaming directly into tables (no staging files, seconds latency) + Dynamic Tables (declarative continuous SQL transforms, target lag). Open assembly:
- **Event/file plane:** Kafka/Redpanda (durable log) or object-storage notifications + queue; **Debezium / Flink CDC / Airbyte (ELv2 platform — check licence split: connectors/CDK MIT in sources) / dlt / Meltano-Singer** for SaaS/DB sources (Fivetran itself is proprietary — the “open alternative” is Airbyte/dlt/SeaTunnel, with connector breadth/quality as the gap); **Benthos → Redpanda Connect** (Go, single-binary declarative stream processor, 200+ connectors in comparisons; note licence split in sources: original Benthos Apache-2.0, Redpanda Connect maintained builds source-available/RCL — verify) for routing/light transforms.
- **Stream processing into Iceberg:** **Arroyo** (Rust, DataFusion SQL engine, Apache-2.0, pre-1.0; acquired by Cloudflare Apr 2025, powers Pipelines, engine remains OSS https://www.arroyo.dev/blog/arroyo-0-15-0/), **RisingWave** (Rust streaming *database*, Postgres wire, native CDC without Kafka/Debezium, materialised views, Iceberg sink with `type='upsert'`, commits every checkpoint ~10–60 s https://risingwave.com/blog/real-time-analytics-apache-iceberg-risingwave/), **Flink** (the incumbent: Iceberg sink, Paimon origin, exactly-once via two-phase commit to catalog), **Spark Structured Streaming** (Delta/Iceberg sinks, `availableNow` patterns). All of them produce the small-files firehose (§2.7) — **streaming ingest without scheduled compaction is an outage in slow motion.**
- **Streaming upserts into Iceberg, honestly:** writer emits equality/position deletes or v3 deletion vectors + new data files, commits new snapshot per checkpoint (commit rate vs metadata bloat trade-off), readers merge on read until compaction rewrites. Primary-key table models (Paimon, Hudi, Doris/StarRocks PK) handle upserts *inside* the engine far more naturally — if upsert freshness is the wedge workload, that argues for those engines over pure Iceberg+Trino.
- **Verdict:** INGESTION IS ASSEMBLY, NOT INVENTION — borrow Kafka + (Arroyo|RisingWave|Flink) + Airbyte/dlt; BUILD the Snowpipe product surface (exactly-once bookkeeping per file/offset in the metadata store, schema-drift handling, load history, error queues, per-tenant ingest metering).

### 5.2 VARIANT / semi-structured
Snowflake's original trick (2016 paper §4.3): schema-on-write *inference* — frequently occurring JSON paths are automatically extracted into typed, columnar sub-columns with their own statistics/pruning, remainder stays in VARIANT; queries address paths with dot/bracket notation.
- **Iceberg/Parquet v3 VARIANT:** binary, self-describing per-value type, with *shredding* (hot fields extracted to typed columns, bounds/pushdown on shredded fields) — the open standardisation of Snowflake's idea, now in Parquet + Iceberg v3 (§2.2).
- **DuckDB:** `JSON` (text, extension) historically; **VARIANT type in 1.5 (Mar 2026)** — binary per-row typed, automatic shredding claims up to 100× on JSON analysis in release materials https://duckdb.org/docs/2.0/sql/data_types/overview
- **ClickHouse:** `JSON` type with typed subcolumns per path (limit `max_dynamic_paths`, default 1,024 in cited analysis; overflow → shared-data storage, slower), plus `Dynamic` (per-value type without schema) and `Variant` (declared union of types) — production since 25.3 in write-ups https://clickhouse.com/docs/reference/data-types/index
- **DataFusion:** JSON via Arrow struct/map/list + functions; VARIANT support follows Arrow/Parquet-variant Rust crates — less integrated than DuckDB/ClickHouse today; shredding behaviour is engine work you'd verify, not assume.
- **Doris VARIANT:** sub-columnises hot JSON paths similarly (vendor benchmark claims vs ClickHouse/ES on agent-log JSON — treat as vendor data).
- **Verdict:** Borrow the *format* (Parquet/Iceberg VARIANT + shredding); the *engine experience* (path statistics, pruning, dynamic-path overflow behaviour) differs enough per engine that semi-structured performance must be benchmarked on your engine choice, not inferred from the spec.

## 6. Real Projects That Tried This — Case Studies

### 6.1 MotherDuck (DuckDB in the cloud)
Serverless warehouse on DuckDB: **hypertenancy** (“everybody gets a duck” — per-user/customer isolated DuckDB instance, “Ducklings”, ~100 ms spin-up claim, shutdown on idle), shared storage, **dual/hybrid execution** (local DuckDB in browser/Wasm or Python joins local files with cloud tables; optimizer splits execution local vs cloud; Postgres wire endpoint for cloud-only clients), DuckLake for large-write/small-read workloads. CEO Jordan Tigani (ex-BigQuery) argues workload management complexity is *avoided, not solved*, by isolation, and that most workloads' *scanned* data fits one big node (largest instance ≈ Snowflake 3XL hardware). Sources: https://motherduck.com/duckdb-book-summary-chapter7/ ; https://shiftmag.dev/motherduck-ceo-says-single-node-analytics-can-outperform-distributed-systems-12404/ ; self-hosting graduation-path post (build-vs-buy framing, “top-right quadrant = you are now a database company”) https://motherduck.com/blog/self-hosting-duckdb-road-to-production/
**Lesson for opensnow:** The fastest credible Snowflake alternative shipped by *refusing* distributed execution and monetising single-node + isolation + UX. Its limits (per-query single node, DuckDB writer model) are the price, stated openly.

### 6.2 Firebolt
Proprietary warehouse built from scratch (C++ vectorized, own F3 format): three-way decoupling (compute / storage / metadata service for ACID + distributed writes), sparse + aggregating + join indexes, aggressive range pruning, engines as SQL-defined isolated compute. Now also Iceberg support + Firebolt Core (deploy-anywhere edition). **Lesson:** Indexing + format co-design *does* beat generic micro-partition scanning on selective workloads — and it took a well-funded company years of closed development to do it; none of that engine is borrowable. https://www.firebolt.io/comparison/firebolt-vs-redshift ; whitepaper summary https://pub-mediabox-storage.rxweb-prd.com/exhibitor/document/exh-3116ec6a-caeb-4205-943b-970c9669489c/0c05420b-02c5-4560-b57a-a1bc717cd245.pdf

### 6.3 Bauplan
Python-first lakehouse on Iceberg + Nessie-style branching, FaaS/ephemeral execution. Started on a **DuckDB fork** (added `EXPLAIN SCANS` to split S3 scans/pushdown from SQL logic because DuckDB insisted on controlling I/O; found Iceberg-DuckDB buggy in their June 2025 tests), then **migrated all SQL to DataFusion** (flag flipped 2025): reasons stated — DataFusion is a *project for builders* (extensible optimizer/parser, Arrow-first, community roadmap) vs DuckDB a *product for end users* (own lakehouse format, zero-dependency ethos); fork maintenance cost exceeded benefits; removed their only C++ dependency. Now ~200k jobs/week claimed. https://bauplanlabs.com/post/duck-hunt-moving-bauplan-from-duckdb-to-datafusion
**Lesson:** The build-vs-borrow decision is about *control surface*, not benchmark speed. If you need to own scan planning, caching and branching, pick the engine designed to be taken apart — even if the embedded product benchmarks similarly.

### 6.4 Tobiko / SQLMesh, Smallpond, others named in the mission
- **Tobiko Data / SQLMesh:** Not a warehouse — a transformation framework (SQLGlot-based, virtual data environments, plan/apply, column lineage, Apache-2.0 core + Tobiko Cloud) https://sqlmesh.readthedocs.io/en/stable/faq/faq/ . Relevance: the *dev-environment / branching UX* layer opensnow would integrate (or compete with dbt on), and proof that virtual environments over warehouse snapshots are a valued product independent of the engine.
- **smallpond (DeepSeek, OSS):** Distributed *data-processing framework* on DuckDB + 3FS — partition work across nodes, each runs DuckDB. Not a multi-user SQL warehouse (§4.3). Lesson: even DeepSeek's answer is orchestration-over-DuckDB, not distributed DuckDB.
- **GlareDB, Seafowl, Definite, BemiDB etc.:** DataFusion/DuckDB-based products that pivoted, stalled or stayed niche — pattern: engine demo in weeks, warehouse product (auth, concurrency, ops, sales) in years. (Single-source / ecosystem observation — flagged as lower confidence.)

### 6.5 ClickHouse Cloud
§1.3: OSS shared-nothing → Cloud required *new* SharedMergeTree, shared storage, Keeper-based coordination, stateless compute and finally a Shared Catalog — a multi-year re-architecture by the engine's own creators, kept proprietary. **Lesson:** “Separate storage and compute in the OSS engine” is a re-write of the storage engine, not a deployment flag. Budget accordingly if Archetype C forks anything.

### 6.6 Databricks Lakehouse (Delta + Photon + Unity)
Spark (OSS) for distribution + **Photon** (proprietary C++ vectorized engine, 3–8× average speedups claimed over Spark in comparisons) for execution + Delta (OSS) + Unity Catalog (managed; OSS edition later) for governance. **Lesson:** Even the Spark company had to write a closed native engine to reach warehouse performance, and even the “open lakehouse” company's moat layers (Photon, Unity governance depth, predictive optimisation/compaction) are the closed ones. Openness strategy and moat placement are the same decision. https://www.firebolt.io/comparison/bigquery-vs-databricks

### 6.7 BigQuery / Dremel (reference architecture)
Dremel (VLDB 2010) → BigQuery: fully disaggregated — Colossus storage (Capacitor columnar format), Jupiter petabit network, Borg orchestration, Dremel execution *tree* (root → intermediate aggregators → thousands of leaf “slots” reading shards, in-memory shuffle), serverless multi-tenant slot allocation, per-TB-scanned (or capacity) billing. No infrastructure surface at all for users. **Lesson:** BigQuery is the proof that the *services/scheduling layer at planetary scale* is the product; its shuffle-over-network bet only pays with a custom network + storage stack no startup replicates — opensnow archetypes should not imitate Dremel's shape, only its lesson that scheduling + metering + isolation are first-class. https://www.datumo.io/blog/snowflake-vs-databricks-vs-bigquery

### 6.8 Snowflake's own papers (reference architecture)
- **Dageville et al., “The Snowflake Elastic Data Warehouse”, SIGMOD 2016** https://www.cs.cmu.edu/~15721-f24/papers/Snowflake.pdf?ref=greybeam-blog.ghost.io : multi-cluster shared-data; three layers (storage / compute “virtual warehouses” / cloud services); stateless services over replicated metadata; snapshot isolation over immutable files; semi-structured columnarisation; “not based on Hadoop”, built from scratch (C++ engine + Java services in later accounts).
- **FoundationDB blog (Snowflake, 2018, updated)** §9.
- **Execution Anchor engineering blog (2025–26):** even today Snowflake publishes hard distributed-correctness work in the services layer — binding each query to exactly one Global Services instance via an FDB-recorded anchor, guarding every FDB transaction — evidence the services layer is still where correctness engineering concentrates https://www.snowflake.com/en/blog/engineering/snowflake-distributed-query-execution-anchors/

### 6.9 Dremel / Velox / Photon — what closed engines teach about vectorization
All three converge: (1) vectorized native execution over columnar batches is table stakes (JVM/row engines lose); (2) the winning engines are *libraries decoupled from their hosts* (Velox under Presto/Spark, Photon under Spark, Dremel under BigQuery's serving layer) — composability was designed in, not extracted later; (3) consistency of function semantics across engines was Velox's founding motivation — SQL dialect/semantics drift is a correctness/trust problem, not a docs problem, for any opensnow that federates engines.

### 6.10 Failures / where projects stall — synthesis of cases above
1. **Forking an embedded engine to make it distributed** (Bauplan/DuckDB) → fork tax > engine benefit → migrate to builder toolkit.
2. **Underestimating maintenance services** (DIY Iceberg: compaction, expiry, version-skew correctness bugs) → “14 months, two platform leads burned, first pipeline not shipped” composite in DIY-tax reporting (vendor-sourced, directional) https://www.techtimes.com/articles/315054/20260310/self-hosted-data-lakehouse-diy-cost.htm
3. **Cloud separation as an afterthought** (ClickHouse) → storage-engine rewrite.
4. **Engine-first, services-never** (numerous DataFusion/DuckDB startups) → demos without auth/multi-tenancy/billing/ops don't convert to warehouse revenue.
5. **Single-node ceiling discovered late** (DuckDB serving write-ups) → concurrency/HA/writer model must be designed at the *product* layer (hypertenancy or MPP) on day 1, not retrofitted into the engine.

### 7.1 Layer-by-layer: off-the-shelf vs build

| File format | Parquet (mature) | Writer tuning, VARIANT shredding config | Small |
| Table format | Iceberg v2 (mature) / Delta | Compaction/expiry/GC **service**, clustering service, clone ref-counting/GC protection, branch workflows | **Medium–Large (permanent service)** |

| Ingestion | Kafka, Debezium, Airbyte/dlt, Arroyo/RisingWave/Flink | Snowpipe product surface, load history, schema drift, ingest metering | Medium–Large |

| AI / Cortex analogue | Lance + vector indexes, MCP servers per catalog/engine | Integrated governance of models/features, in-warehouse ML/LLM serving, agent access controls | Large (and moving) |

### 7.2 Team / time — what sources actually cite
- **DIY lakehouse assembly (no new engine):** Onehouse-cited estimate: **3–6 FTE, 6+ months before functional**, maintenance 30–40 % of initial build effort per year; Wakefield-cited ~$520k/yr org maintenance cost, engineers spending ~half their time maintaining pipelines https://www.techtimes.com/articles/315054/20260310/self-hosted-data-lakehouse-diy-cost.htm — *vendor-adjacent sources, treat as order-of-magnitude, not a quote.*
- **From-scratch engine (historical anchors, not estimates):** Snowflake: founded 2012, SIGMOD system by 2014–16, GA 2015 — with Oracle/Vectorwise veterans and very large funding; ClickHouse Cloud separation: ~2022–26 and counting, by the engine's own team; Firebolt/Photon: multi-year closed efforts by large teams. No credible source found claims a Snowflake-parity warehouse from scratch in <2–3 years; any plan implying otherwise should be treated as a scoping error (see Could Not Verify).
- **MotherDuck counter-anchor:** a *non-parity, single-node* warehouse product reached market far faster by borrowing DuckDB wholesale and building only services + hypertenant fleet + UX — the delta between MotherDuck's scope and Snowflake parity *is* the distributed-execution + global-services scope.

### 7.3 Language trade-offs
- **Engine: Rust vs C++.** Rust (DataFusion ecosystem): memory safety, no GC, Arrow-native crates, async ecosystem, smaller hiring pool + steep curve, faster *safe* iteration for a new team. C++ (DuckDB/ClickHouse/Velox): deepest existing code to borrow, SIMD/control, largest systems hiring pool historically, memory-safety risk and slower safe iteration; forking C++ is what Bauplan exited. **Go for engine:** no serious vectorized engine is Go-native (chDB/DuckDB via cgo are the pattern) — Go engines pay FFI tax; Go shines in control plane / Benthos-class tooling.
- **Control plane / services:** Go (static binaries, concurrency, K8s ecosystem — Lakekeeper is Rust, Polaris is Java, Gravitino is Java; language follows catalog choice), Rust (if DataFusion-centric, one-language stack simplifies hiring/FFI), TypeScript (fastest for API/UI-adjacent services, UI team overlap; weaker for high-throughput metadata paths), Java (Calcite/Trino/Polaris gravity). Postgres-wire compatibility (RisingWave/DuckDB-Postgres dialect) reduces client friction regardless of implementation language.
- **Rule of thumb from cases:** *match the language of the engine you borrow most deeply* — every FFI boundary (JVM↔native in Comet/Gluten, Go↔DuckDB cgo) becomes a permanent memory-accounting/spill/observability seam (documented in Comet/Velox-Lance issues https://github.com/lance-format/lance-c/issues/34).

## 9. (b) Hardest Unsolved Pieces (ranked by evidence of projects stalling there)

1. **Distributed scheduling + shuffle + fault tolerance with interactive latency** — stage retry semantics, skew, adaptive re-planning, shuffle storage; Ballista is a starting point, Spark/Trino are the only OSS “done” answers and they own your architecture if you take them.
2. **Global cost-based optimizer quality** — join ordering + statistics freshness at Snowflake/BigQuery level is a decade of compounding work; a mediocre optimizer silently makes a fast engine look slow on real (multi-join, messy) workloads.
3. **Multi-tenant services correctness** — transactions/locks/sessions/sharing/billing over a metadata store, with upgrades that never break in-flight metadata (Snowflake still publishes papers'-worth of engineering here: execution anchors, §6.8).
4. **Table maintenance as a perpetual, invisible service** — compaction, clustering, expiry, orphan GC, deletion-vector merging, with clone/share reference safety and cost controls; failure mode is slow degradation, not an error.
5. **Concurrency + admission + workload isolation** — fairness, queueing, spill/memory arbitration across tenants; hypertenancy dodges it at fleet cost, MPP engines embody years of tuning for it.
6. **Governance that engines actually enforce** — row/column policies, masking, lineage/access history consistent across *every* engine that can read the tables (a second engine is a governance bypass unless the catalog/credential layer enforces it).
7. **Warm-start economics** — suspend/resume + cache warmth + per-second billing without burning margin on warm pools; physics (cluster start, cache refill) vs serverless expectations.
8. **SQL/dialect compatibility** — Snowflake-dialect migration (functions, semi-structured operators, DDL) is a long tail that determines enterprise adoption more than benchmarks.

## 10. (c) What Snowflake's FoundationDB / Metadata and Optimizer Teach — where the real moat is

Primary source: Snowflake, “How FoundationDB Powers Snowflake Metadata Forward” https://www.snowflake.com/en/blog/how-foundationdb-powers-snowflake-metadata-forward/ (Snowflake on FDB since 2014) + SIGMOD 2016 + Execution Anchor blog (§6.8).

- **Metadata is not a catalog table; it is the operating system.** In FDB Snowflake stores: catalog definitions, users/sessions, access control, copy/load history, *every executed statement + its statistics*, transaction state, lock queues (implemented with FDB `watch` notifications), data-distribution info, server registry, encryption keys — triple-replicated across AZs, encrypted, behind a versioned object-mapping layer that handles schema definition/evolution and blue-green metadata upgrades while stateless services keep running.
- **Differentiating features fall out of metadata transactions for free — once that layer exists.** Snowflake's own words: features were built “as purely metadata operations” — **zero-copy clone** (new object → pointers to same micro-partitions), **time travel** (keep old pointer sets), **data sharing** (grant another account's services layer access to your pointer set), **instant elasticity / separate warehouses** (services layer assigns any compute to the same metadata-defined data). None of these required touching data files. *That* is why competitors with equally fast engines but file-based catalogs ship these features slowly and buggily: they are re-implementing a transactional metadata database on top of manifest files.
- **The optimizer is a metadata consumer, so metadata quality = query quality.** Per-micro-partition, per-column statistics in FDB drive pruning (no indexes needed), join planning, and metadata-only query answers. Iceberg manifests replicate the *statistics* part of this, but distributed across files that must be listed, cached and compacted — the architectural tax DuckLake and Snowflake both avoid by keeping stats in a queryable database.
- **Correctness engineering concentrates there, permanently.** Lock queues via watches in 2016; execution anchors binding queries to one services instance in 2025 — the services layer is not “finished” after a decade at Snowflake scale. Budget opensnow's services layer as a permanent, senior team, not scaffolding.
- **Moat conclusion:** Engines commoditise (Velox/DataFusion/DuckDB prove it), formats commoditise (Iceberg won), *integrated, transactional, global metadata + optimizer + governance does not* — because it compounds: every feature, every tenant, every query's history makes it richer and harder to replicate. An opensnow strategy is therefore really a choice of *how to build that layer* (Postgres → FDB/Cockroach evolution path, Polaris for table commits, statistics as a first-class service) while borrowing everything below it — or, like MotherDuck, a choice to compete where that layer can stay deliberately small.
